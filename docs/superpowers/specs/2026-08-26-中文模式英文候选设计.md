# 中文模式英文候选设计

日期：2026-08-26

## 目标

在中文输入模式下，把英文单词候选混入普通候选流。核心场景不是"打 book 出 book"，而是**拼写辅助**：忘了单词怎么拼，打出前几个字母让输入法补全（`belie` → believe、`palad` → palladium）。

英文模式（Shift 切换后）的行为完全不变。现有 `EnglishSettings.enabled` 只作用于英文模式，本设计新增一个独立开关，两者互不影响。

## 非目标

- 不做英文语法纠错、不做词组联想。
- 不改动英文模式下的任何行为。
- 不引入在线服务，词库全部离线随包。

## 〇、实测修正（2026-08-26，首次实机后重写）

初版规则实机后立刻暴露问题：`wom` 给出 women/woman/womb 把「我没」「我吗」挤走，`tzn` 给出 tarzan，`buco` 给出 bucolic。三个独立成因：

1. **子序列联想没有关掉。** `EnglishLexicon::query` 在输入 ≥3 字母时会做子序列匹配，那是给英文模式的缩写输入用的（打 `jiy` 要 `jimmy`）。中文模式下字母是拼音，按子序列凑英文词只会得到 `tzn`→tarzan、`buhc`→buddhic 这类毫无关系的结果。中文模式必须传 `allow_subsequence = false`。
2. **低频层没有门槛。** 词库最底层只有词形没有词频，`bucolic`(155,354)、`nizey`(188,446)、`tizwin`(162,870) 全部涌入。前缀匹配须设权重下限 200,000。
3. **判定信号选错了。** 初版用 `covers_all_input` 判断「中文候选是否可信」，这在全拼成立、在双拼完全不成立——`wom` = wo + m、`niz` = ni + z 的尾部半音节是双拼常态，引擎本就有意补全（`mkt` 给「明天」）。该信号在双拼下必须忽略。

### 重新标定后的规则

给不给：

| 条件 | 结果 |
| --- | --- |
| 长度 < 4 且非全词 | 不给（`wom` `niz` `tzn` `jiy`） |
| 长度 < 4 且全词但中文 ≥ 200,000 | 不给（`bus` → 不是 501,670） |
| 前缀目标词权重 < 200,000 | 不给（`buco` → bucolic） |
| 全词匹配 | 给，无论多生僻（`bucolic` `quixotic` `obsidian`） |

排第几：

| 条件 | 位置 |
| --- | --- |
| 无中文候选 | 1 |
| 长度 2 | 5 |
| 全词 且 长度 ≥ 5 且 中文 < 100,000 | 1 |
| 其余 | 2 |

### 为何不复刻竞品

实测搜狗与微信在同一批输入上行为相互矛盾：`sun` 搜狗给第 3、微信不给；`hous` 搜狗给、微信不给；`car` 搜狗第 1、微信补出 carbon 占第 1；`bucolic` 搜狗第 2 而微信第 1。同一词在搜狗上先后两次位置不同（第 2 → 第 1），说明其结果受用户学习影响，不可复现。

因此本设计只采纳两家的**共识**——`bus` 不给、`big`/`men`/`car` 给、生僻词全词才给、短前缀不给——分歧处按「可解释、可预期」自行决定，以实际使用手感为准，不以对齐某一家为目标。

## 一、候选位置规则

同一串字母可能同时是拼音和英文词。竞品在全拼下的实际表现（用户实测搜狗、微信）显示，排序由两个信号共同决定，而不是固定位置：

| 输入 | 中文最佳（PiInput 全拼实测） | 拼音是否被完整消耗 | 搜狗把英文放在 |
| --- | --- | --- | --- |
| `he` | 和 `he` 6,252,031 | 是 | 不给英文 |
| `an` | 按 `an` 3,826,950 | 是 | 第 8 |
| `name` | 那么 `na'me` 501,795 | 是 | 第 2 |
| `code` | 错的 `cuo'de` 105,000 | 是 | 第 1 |
| `time` | 提 `ti` 1,026,285 | 否，只吃掉 `ti` | 第 1 |
| `book` | 把 `ba`（`b` 简拼） | 否 | 第 1 |
| `with` | 简拼牵强匹配 | 否 | 第 1 |
| `apple` | 按 / 爱（`a` 前缀） | 否 | 第 1 |

据此定义查表规则。表中的"中文最佳"指中文候选列表第一项。

| 中文侧状态 | 英文起始位置 |
| --- | --- |
| 无中文候选 | 1 |
| 拼音未被完整消耗（简拼、前缀或模糊匹配） | 1 |
| 完整匹配且词频 < 200,000 | 1 |
| 完整匹配且词频 200,000 ~ 1,000,000 | 2 |
| 完整匹配且词频 1,000,000 ~ 5,000,000 | 5 |
| 完整匹配且词频 > 5,000,000 | 不给英文候选 |

"拼音是否被完整消耗"直接读候选自带的 `CandidateEvidence::covers_all_input`，无需自行比对字符串。该字段已在解码阶段算好。

**双拼与全拼共用这套规则，但各自一套阈值常量。** 双拼下四个字母极易凑成两个合法音节，`time`、`name`、`code` 全都能拼出高频中文，"完整消耗"这个信号比全拼弱得多，因此双拼的词频阈值需要单独标定，否则英文会抢得过凶。

## 二、三方优先级

同一串字母最多有三个候选来源，优先级固定：

```
快捷命令（保持配置位置） > 中文候选 > 英文候选
```

- 快捷命令按用户配置的位置插入，位置不受英文候选影响。`calc` 的计算器入口仍在候选 2，`time` 的 🕗时间入口仍在其配置位。
- 英文候选从第一节算出的起始位置开始插入，**不得挤占快捷命令已占用的位置**，遇到则顺延。
- 结果示例：`calc` → 1 中文候选 · 2 计算器 · 3 calculate · 4 calculation。

快捷命令的识别不需要新增标记：`CandidateKind` 已区分 `symbol_tool_action`、`emoji_tool_action`、`settings_action`、`launch_action` 与 `datetime_group`，这些一律视为不可挤占的占位。快捷命令由 `Engine::splice_symbol_shortcuts` 在解码阶段按 `shortcut.position` 插入，早于英文候选的注入点，因此注入时它们已在列表中。

理由：快捷命令是用户显式配置的触发码，优先级应高于词库自动匹配；且现有肌肉记忆（`calc` 按 2 开计算器）不能因为开启一个新开关而失效。

## 三、词库分层

保留现有 24,323 词表作高频层，引入 8～15 万词的开源英语词频表作低频层。

**注意现有词表第二列是排名倒数，不是真实词频**（`the` 24323、`of` 24322、`time` 24264 即第 60 名、`codex` 5163 即第 19161 名）。合并时必须给两层划定不重叠的分数区间，否则大表中某个词的原始词频可能盖过现有高频词。

| 层 | 来源 | 分数区间 |
| --- | --- | --- |
| 用户学习词 | 用户上屏过的词 | > 1,024,323 |
| 高频层 | 现有 24,323 词表 | 1,000,001 ~ 1,024,323 |
| 低频层 | 开源大表新增词 | 1 ~ 999,999 |

低频层再设一个词频下限，低于该下限的冷僻词不进候选，用于控制噪音。下限值在实施阶段用真实输入标定。

**英文候选参与学习。** 复用现有 `EnglishSettings.user_learning` 与 `user_dictionary` 机制，不另起一套。用户上屏过的英文词升入学习层，因此大表也覆盖不到的词（如领域专名）打过一次即可补全。学习数据在中文模式与英文模式之间共享——用户在哪个模式打过这个词并不重要。

词表选型需逐一核对许可证。SCOWL、wordfreq、google-10000-english 的许可均可用，但须按项目既有规矩（YeSymbol、YeTool 的处理方式）安装到 `bin/licenses/` 并写入 `THIRD_PARTY_NOTICES.md`。

## 四、触发条件

全部满足才产生英文候选：

- 当前为中文输入模式；
- 新增开关已开启；
- 输入串全部为 ASCII 字母（含数字或符号时不触发）；
- 输入串长度 ≥ 3。

### 长度分档（实测后收紧）

设计初稿写的是"长度 ≥ 2"。真机试用后用户的判断是：**"打字的过程中不要让我
感觉频繁出来一堆英文，而想用英文的时候又能匹配出来。"** 按这条标准重新标定
后，长度不再是单一门槛，而是分三档决定"查多大的词库、要不要求全词"：

| 输入长度 | 词库范围 | 是否要求全词 | 理由 |
| --- | --- | --- | --- |
| ≤ 2 | 不查 | — | 双拼下正好一个音节，而那里住着 我(29,569,261)、的(76,938,354)，英文赢不了 |
| 3 | 仅基础词库（权重 ≥ 1,000,000） | 是，且中文权重 ≥ 200,000 时否决 | 三字母在双拼下必然是词中间：`wom` 是 我+m，`car` 是 擦+r |
| 4 | 仅基础词库 | 否，可前缀补全 | `wome` → women；但 `buco` → bucolic 被基础词库门槛挡住 |
| ≥ 5 | 完整词库（权重 ≥ 200,000） | 否 | 输入已经表明意图，拼写辅助的主场 |

**全词永远豁免词频门槛。** 把一个词完整打出来是对意图的声明，再生僻也算数：
`bucolic` 给，`bucoli` 不给，差别不在词而在有没有打完。

三字母档的中文否决线来自实测：`bus` 的 不是 是 501,670，搜狗与微信都不给英文；
`car` 的 擦 是 172,541，两家都给。200,000 落在这两者之间。

竞品对齐不可行——同一批输入上搜狗与微信互相矛盾，且搜狗的结果会随用户学习
漂移（同一词先后两次位置不同）。因此判据改为"用户觉得不烦"，而非"和竞品一致"。

### 词库侧的拼音过滤

规则挡不住一类情况：`xie`(洗耳 1,505)、`mei`(么 9,727)、`dui`(督察 162,515)
的中文权重**低于**否决线，中文侧拦不住，但它们在英文词库里确实存在（wordfreq
统计真实文本，汉语拼音在英文语境里出现得不少）。

这类词在生成阶段剔除，判据是两条同时成立：是 `src/pinyin_syllables.inc` 里的
合法音节，且 zipf < 4.0。第二条不能省——`can`、`he`、`me`、`man`、`men`、
`run`、`sun`、`gun`、`fan`、`ban`、`pan`、`tan` 全是合法音节，只按音节剔会把
功能本身弄坏。4.0 是量出来的：该删的最高 `ni` 3.93，该留的最低 `tan` 4.01。

不采用更宽的"短词必须常用"，因为**这份词库英文模式共用**，那条规则会连带删掉
`wane`(2.83)、`dow`(3.63) 这类真英文词，英文模式也就打不出来了。详见
`third_party/english-wordlist/PROVENANCE.md`。

## 五、候选内容

- 前缀补全，最多 2 个（初稿为 3，实测"一堆英文"后下调），复用 `EnglishLexicon` 已有的 `prefix_index_` 与 `completion_preferences_`，无需新建索引。
- 全词命中且长度 < 5 时只给该词本身，不再拖出 `catch`、`cathedral` 之类的同前缀长词。
- 精确匹配的词若存在，排在补全结果之前。
- 大小写跟随输入形态：`book` → book、`Book` → Book、`BOOK` → BOOK。词库中本身为专有名词形态的词（如 Apple）保持其原形。

## 六、架构落点

英文候选的注入点在候选组装的最后一步，即 `HostSession::snapshot()`（`src/host_session.cpp`）。该函数已负责符号候选的组装，是三方来源唯一汇合的位置。

但 `host_session.cpp` 已有 781 行，直接在其中展开分层查表与位置计算会使其继续膨胀。因此新增一个独立组件承担规则计算：

```
src/english_completion.h / .cpp

  struct EnglishCompletionPlan {
      std::size_t start_position;      // 0 表示不插入
      std::vector<std::string> words;
  };

  EnglishCompletionPlan plan_english_completion(
      std::string_view input,
      const ChineseCandidateSummary& chinese,   // 最佳候选的 pinyin 与 score
      const EnglishLexicon& lexicon,
      const EnglishCompletionSettings& settings);
```

该组件是纯函数：不持有状态、不接触窗口与协议，输入是"输入串 + 中文侧摘要 + 词库 + 设置"，输出是"插到第几位 + 插哪些词"。`HostSession::snapshot()` 只负责调用它并按返回的位置合并，合并时跳过快捷命令已占用的位置。

这样第一节的查表规则、第三节的分层评分、第四节的触发条件全部可以脱离 TSF、脱离 Host 进程单独测试。

## 七、设置

在现有 `[english]` 段新增开关，与英文模式的 `enabled` 并列且独立：

```ini
[english]
enabled = false                  ; 英文模式下的英文候选（现有，不变）
chinese_mode_completion = false  ; 中文模式下混入英文候选（新增）
```

设置程序中作为一个独立复选框呈现，文案需明确它只影响中文模式。默认关闭。

## 八、测试策略

**单元测试**（`tests/unit/english_completion_tests.cpp`，新增）

- 位置查表：第一节表格的六个区间各一个用例，使用本文档中的真实词频数据（和 6,252,031 / 按 3,826,950 / 那么 501,795 / 错的 105,000）。
- 未完整消耗的判定：`time` → `ti`、`book` → `ba` 应判为未完整。
- 触发条件：单字母不触发、含数字不触发、英文模式不触发、开关关闭不触发。
- 大小写三种形态。
- 分层评分：学习词 > 高频层 > 低频层，且低频层不得越过高频层。

**回归测试**

- 开关关闭时，中文候选序列必须与开启此功能之前逐字节相同。这是最重要的一条：新功能默认关闭，不得对现有用户产生任何影响。
- 快捷命令位置不被英文候选挤占：`calc`、`time`、`jsq`、`sj` 各一个用例。
- `piinput-keystroke-latency` 不得退化：前缀查询在每次按键路径上，需确认其代价可接受。

## 九、实施顺序

一次交付完整功能，包含大词库。内部有依赖顺序：

1. **规则组件 + 单测**：`english_completion` 纯函数与位置查表，先用现有 24,323 词库验证规则本身。
2. **词库分层**：选定开源大表，核对许可证，构建分层评分，标定低频下限。
3. **接入候选流**：`HostSession::snapshot()` 合并，处理与快捷命令的位置关系。
4. **学习打通**：英文上屏进入学习层，中英文模式共享。
5. **设置项与 UI**：配置读写、设置程序复选框。
6. **回归验证**：开关关闭时中文候选逐字节不变、快捷命令位置不受影响、按键延迟不退化。

先做规则再做词库，是因为规则的正确性可以用少量已知词验证，而词库标定需要规则就位后才能判断阈值是否合适。
