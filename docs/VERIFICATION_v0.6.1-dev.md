# PiInput v0.6.1-dev 验证记录

## 本版阻断问题

用户反馈：连续输入「我，他们。我们明天，去哪里？明天、后天！打后天。」整体偏卡，标点之后再输入文字最明显。

## 定位过程

先用常驻 Host 的真实进程夹具区分传输开销与引擎开销：

- 空载 `health` 往返 P95 为 809 微秒，而该请求几乎不做任何工作；
- 逐键 `key_event` 往返 P95 为 2582 微秒；
- 同一输入的引擎查询在基准工具中只有 40～140 微秒。

三个数字对不上，说明大部分时间既不在拼音解码也不在词库查询。逐项核对后确认四处真实开销：

1. `shim_pipe_transport.cpp` 与 `pipe_server.cpp` 每读一条消息就新建并清零 `host_header_bytes + host_max_payload_bytes`（约 1 MiB）的向量，而真实回包只有几 KB。每次按键至少发生两次（按键消息与光标消息），双方各一份。
2. `PipeServer::run` 判断组合边界时调用 `SessionManager::snapshot()`，复制整份候选快照仅为读取 `raw` 是否为空；随后 `poll_settings_at_composition_boundary()` 对 `settings.ini` 做两次 `std::filesystem` 查询，文件不存在时还会抛出并捕获一次 `filesystem_error`。该路径只在组合为空的按键上触发，也就是每个词的首字母和每个标点之后的第一个字母，与用户描述的现象完全吻合。
3. Host 写出回包后又用 `decode_host_reply` 把同一段字节解析回来，只为把候选交给候选栏，等于每键多做一次全量候选字符串解码。
4. 基准工具固定按 10 条候选测量，而 Host 实际请求 `CandidateSettings::max_items`（90 条）。同一输入在 90 条下耗时约为 10 条的 10 倍：`wom` 47 → 590 微秒，`womfmkt` 129 → 1191 微秒。真实热路径此前没有被任何门禁覆盖。

## 修复

- 两端各自持有一个 16 KiB 起步、按 `ERROR_MORE_DATA` 增长且不再缩小的复用读缓冲区；
- 新增 `SessionManager::at_composition_boundary()` 与 `HostSession::composing()`，边界判断不再复制快照；
- `SettingsFileReader::try_metadata()` 用一次 `directory_entry` 刷新配合 `error_code` 完成非抛出探测，缺失设置文件不再每键抛异常；
- `SessionManager::dispatch` 可直接输出 `HostReply`，Host 不再解码自己的回包；
- 句子解码进入定长 beam 前先用整数比较判定能否入选，避免为必然淘汰的路径复制句子文本；
- 未完成音节的补全阶段把已消费音节前缀提到路径与词的双重循环之外，并把补全词与句子前缀的终端组合预算限定为 8 条，句子 beam 本身不变；
- 候选栏每键只做一次 UTF-16 候选转换，几何未变化时不再重复 `SetWindowPos` 与窗口区域重建；
- `candidate_items_per_row` 只接收前若干列；`encode_host_reply` 预留缓冲区；`FinalEditKeyQueue` 增加 64 键上限。

## 实测结果

真实 101,472 词二进制词库，本机 Windows x64 Release：

- 空载 IPC 往返 P95：809 → 71 微秒，最大值 1106 → 295 微秒；
- 逐键 Host 往返 P95：`womfmktm` 2582 → 1417 微秒，`qvnali` 1653 → 1270 微秒；
- 词—标点—词链路 P95：2484 → 1446 微秒；
- 引擎查询（`limit=90`）：`wom` 590 → 197 微秒，`womfm` 788 → 243 微秒，`womfmkt` 1191 → 341 微秒，`womfmktm` 398 → 74 微秒，`biruwoycuibuv` 约 1880 → 610 微秒；
- 整句 41 次按键：P50 78 微秒，P95 1405 微秒，标点后首字母 P95 121 微秒。

## 候选质量确认

修复前后逐条比对，首选与顺序均未变化：

- `rug` → 如果、入股、乳沟、如歌、如故、入关；
- `mkt` → 明天；`mktm` → 明天；
- `womfmktm` → 我们明天；`qvnali` → 去哪里；`vegeui` → 这个是；`nijtde` → 你觉得；`zfyh` → 怎样；
- `hztm` → 后天；`dahztm` → 打后天；
- `hlheruhdlq` 与全拼 `huangheruhailiu` → 黄河入海流；
- 全拼 `ganjue` → 感觉；
- `biruwoycuibuv` 候选中包含比如我要是不知道。

## 新增与收紧的门禁

- 新增 `piinput-keystroke-latency`：用真实词库重放整句「我，他们。我们明天，去哪里？明天、后天！打后天。」，逐键测量并单独统计标点后首字母，P95 上限 2 毫秒、单键上限 6 毫秒，同时校验整句提交结果；
- Windows 源码回归新增三项：禁止两端重新出现每消息 1 MiB 缓冲、禁止 Host 重新解码自身回包、要求设置探测使用非抛出路径；
- Host 进程门禁收紧：空载往返 P95 由 5 毫秒收到 2 毫秒，逐键 P95 由 10 毫秒收到 6 毫秒、单键上限由 20 毫秒收到 12 毫秒；
- `piinput-benchmark` 新增 `--limit` 并默认 90，两个外部大词库性能门禁改为按生产页大小运行，实测 P95 分别为 855 微秒与 2070 微秒，仍在既有阈值内。

## 三个长文本真机打字测试

发布后用发布包的 `PiInputHost.exe` 逐键回放 `tests/data/real_world_text_corpus.txt` 的三个长文本，通过真实命名管道协议发送与稳定 Shim 完全相同的消息，并按真人习惯选字：目标词不在首选时用 `=` 翻行、用数字键选取，90 条候选内找不到才退化为提交首选。

- 合计 1912 次真实按键，179 个片段；
- 逐键 P50 约 226～237 微秒，P95 约 1.80～1.83 毫秒，最慢一次 3.73 毫秒；
- 提交之后第一个按键 P95 为 1681～1754 微秒，与普通按键的 1798～1826 微秒处于同一水平，**用户反馈的“标点后更明显”不再存在**；
- 新增门禁 `piinput-typing-latency`：至少 1500 键，逐键 P95 低于 4 毫秒、单键低于 15 毫秒。

同一次测试顺带测得真实连续输入的选词代价：首选命中 54/179（30.2%），第一行内命中 72/179（40.2%），90 条候选内可达 98/179（54.7%）。这属于候选排序质量问题，本版未改动排序逻辑，数字反映的是既有现状，不是本次性能修复引入的回归。完整数据见 `docs/三个长文本打字测试_v0.6.1-dev.md`。

## 用户验证重点

在 Notepad++ 中连续输入：

```text
我，他们。我们明天，去哪里？明天、后天！打后天。
```

重点观察逗号、句号、问号、顿号和感叹号之后继续输入文字时，组合区与候选是否立即跟上。
