### 已修：#2 候选窗点击卡死

**根因**：候选窗是 Host 进程主线程创建的窗口，而窗口消息只会投递给创建它的线程。主线程在
`ConnectNamedPipe` 上同步阻塞等待下一个按键，消息泵却只在**处理完一个管道请求之后**跑一次
（`pipe_server.cpp` 循环末尾）。所以只要没人打字，候选窗就完全不处理消息：点击排进队列没人派发，
工具栏按钮毫无反应，Windows 判定窗口无响应——也就是「卡死」。按键仍然有效，因为每次请求后会泵一次，
这也解释了「点了没反应、一打字又突然响应」。

**修复**：`ConnectionWaiter` 把等待连接放到工作线程，主线程改用 `MsgWaitForMultipleObjects`
同时等待「连接完成」和「窗口消息」，有消息就泵。管道本身仍是同步的——把句柄改成 overlapped 会波及
热路径上的每一次读写，而那条路径已经为卡顿问题返工过好几轮。

**测试**：`tests/host_client_fixture.cpp` 的 `--toolbar-responsive` 原本就声称覆盖「空闲时点击」，
但它在发完按键后立刻点击，恰好赶在 Host 那一轮泵消息之前，是个竞态。现在点击前先等 600ms，
确保 Host 已经阻塞在等待连接上——这才是用户的真实操作节奏（看一眼候选再点）。加上等待后测试立刻复现失败。

### 已修：#4 设置窗口打不开

**根因**：`CreateMutexW` 只承诺「已存在时设置 `ERROR_ALREADY_EXISTS`」，并**不承诺**新建成功时把
last error 清零。代码在调用前没有 `SetLastError`，于是前面 `InitCommonControlsEx` 残留的错误码
可能被误读成「已有实例在运行」，程序随即静默退出——没有窗口，没有提示，退出码 0。

**修复**：调用前显式 `SetLastError(ERROR_SUCCESS)`；并且即使真的判定为「已存在」，若 `FindWindow`
找不到窗口，就说明那是残留的互斥体而非运行中的实例，此时继续创建自己的窗口，而不是静默退出。

**测试**：新增 `tests/settings_window_regression.ps1`，启动设置程序并要求出现真实窗口。修复前
报「exited immediately with code 0 instead of showing a window」，与用户描述一致。

### 已修：#3 候选耗尽后没有单字兜底

**根因**：`mk`、`dddyn` 这类纯声母输入在常规路径下**完全没有解析**——`m` 不是合法音节，`mk` 也不是
任何音节的前缀，`expand_input_prefix` 返回空。于是整个 `Engine::query` 里只有简拼那条路产生候选，
单字兜底那条路从未被触发。`mk` 给完 24 个词就断了。

对照：单音节 `m` 是有 12 个单字候选的（吗 没 面 明 名 马…），因为它走的是未完成音节补全。机制一直在，
只是简拼场景够不着。

**修复**：简拼词组之后，用第一个声母的单字继续填充（复用 `query_completions_unlocked`）。

```text
mk     24 个词 → 48 个（后 24 个是 吗 没 面 明 名 马 美 命 目 满 魔 们…）
dddyn   2 个词 → 24 个
sdsf    8 个词 → 32 个
```

**与搜狗的差异**：搜狗对 `dddyn` 给的是「对对对一年 对对对 滴滴滴 多大的」这类**放宽音节数**的词组，
不只是单字。本次按用户明确要求做的是单字兜底；放宽音节数是另一个策略，会与「补全不猜用户没打的音节」
这条既有规则冲突，没有一并做。
