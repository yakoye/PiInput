# PiInput v0.6.2-dev 版本说明

本版只修两个用户反馈的问题，不改候选排序权重。

## 一、按 Shift 切到英文后打字特别慢

英文候选默认关闭，此时 Host 对每个英文字母返回一次提交。稳定 Shim 收到提交时若没有进行中的组合，此前会 `StartComposition` → `SetText` → `EndComposition` → `SetSelection`，等于每敲一个字母就让宿主程序完整经历一轮输入法状态切换。在 Word、浏览器、Electron 这类程序里这四步各自都要跨边界通知，累积成明显迟滞。

实测确认瓶颈不在 Host：英文直输的 Host 侧逐键 P50 为 181 微秒、P95 为 408 微秒，和中文同级。

修复分两步：

1. 没有进行中组合的提交改用 `ITfInsertAtSelection` 直接在插入点写入，一次操作取代四次。组合区为空时单独输入的中文标点走同一条更快的路径。
2. 但第一步之后仍有迟滞：每个字母仍要**跨进程往返 Host 一次**，再由后台线程回投到应用消息循环才落到文档里。应用消息循环一忙就是几十毫秒。英文直输既没有组合也没有候选，Host 只是把字母原样回传，这一趟完全没有必要。现在 Shim 用「切到英文后第一个字母的回复是否为单字符提交」判定直输模式（英文候选开启时该字母返回的是组合更新，判定自然为否），其后的字母直接在按键处理内同步写入，不再联系 Host。有任何请求在途时自动退回原有顺序路径，避免字母抢在待提交标点之前。

## 二、按 `=` 之后整词候选整行消失

分段取字此前只保留「候选表开头连续可信命中」的条数。像 `kady`、`fwihkk` 这种第一行全是真实词、但只有第一条算可信命中的情况，该计数是 1 甚至 0，于是按 `=` 之后整行真实词被逐字候选顶替。

修复后，用户当前已经看到的整词行一定保留，分段取字追加在其下方，长词段优先、单字兜底的既有顺序不变。真实词库下 `kady` 按一次 `=`：

```text
第 1 行：卡吨 卡顿 卡盾 卡蹾 卡炖 卡蹲     ← 原词行保留
第 2 行：卡 喀 咖 咔 佧 咯                 ← 分段取字追加
第 3 行：垰 胩 鉲 擖 裃
```

## 三、词库缺少「卡顿」

用户反馈 `kady` 的首选是「卡吨」而不是「卡顿」。排查后确认这不是排序公式的问题：**「卡顿」和「卡吨」都不在词库里**，两者都是单字拼接出来的，排序完全由单字权重决定（吨 2100 > 顿 1820），所以「卡吨」赢。

「卡顿」缺失的原因是：它只出现在 `phrase-pinyin-data` 这个**只提供读音、不提供真实词频**的源里。该源共 41 万条、权重统一为 1，按既定规则不能混入常驻词库覆盖 Rime 的真实词频，因此默认的 `resident-hot-v1` 构建把它排除在外。「卡顿」同时不在 Rime 通用词、随包 SCEL 和内置起步词库中，于是彻底缺席。

同样缺失的还有「补全」，它连读音表里都没有，读音按 `bu'quan` 手工给出。

修复：把「卡顿」`ka'dun` 与「补全」`bu'quan` 加入内置起步词库 `data/base_lexicon.tsv`（与此前加入「开悟」「丝滑」相同的机制），并在当前已发布的词库基线上重新编译，条目数由 101,472 变为 101,474。

需要注意：`dicts/` 下的 SCEL 已由发布时的 11 个增加到 24 个，另有一个 12.7 万条的 `dicts/user/网络流行新词.tsv`。按现状整库重建会得到 40 万～52 万条，并使长句验收「固件开发需要熟悉底层寄存器配置和链路状态机」失败，正是产品底线中「冷门专业词污染普通候选」的情形。本版因此没有整库重建，只在已验证的基线上追加这两个词；那批新词库如何取舍留待确认。

顺带查出「闪退」也缺失：它在 `THUOCL_IT.txt` 里，而默认构建只合并 THUOCL 的诗词与成语两个集合。本版未改动该取舍。

## 验证重点

1. 按 Shift 切到英文，连续输入一段英文，观察是否还有明显迟滞；
2. 输入 `kady` 后按一次 `=`，第一行整词候选应保留，逐字候选出现在下方；
3. 输入 `kady`，首选应为「卡顿」；输入 `buquan`，首选应为「补全」。
