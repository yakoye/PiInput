# PiInput v0.7.12 验证记录

## 问题

全拼 `xie` 首选为「西鄂」（词频 6）而非「些」（词频 3752167）。这是 v0.7.9 起记录在案的既有问题。

## 定位

`xie` 解出两种切分：

```text
1. xie
2. xi'e
```

`src/engine.cpp` 的 `add_exact` 按下式分组：

```cpp
const std::size_t group = single ? 2U : (covers_all ? 0U : 1U);
```

「些」是单字 → 第 2 组；「西鄂」两字且 `covers_all` → 第 0 组。`better()` 中 `group` 先于 `parse_rank` 与 `base_weight` 比较，因此次要切分的生僻词压过主切分的常用字。

「单字排在词之后」这条规则本身是对的，但它只在**同一种切分内部**成立。用来比较两种切分时，等于让「字数多」压过「用户实际敲的读法」。

## 两次走错的方案

**其一：把 `group` 改成只看覆盖度**（`covers_all ? 0 : (single ? 2 : 1)`）。`xie`/`xian` 的结果对了，但 `piinput-incremental-decoder` 失败——它用三个同拼音 `a` 的词条（安 / 长长 / 长安，权重相同）断言长词在单字之前。那是**同一切分内**的比较，词优先于字必须保留。

**其二：比较器内按 `same_parse` 分流**（同切分比 group，跨切分比词频）。结果正确，但**破坏了严格弱序**：设 A、B 同切分且 B 组更优但权重更低，C 属另一切分且权重介于两者之间，则 B 优于 A、A 优于 C、C 优于 B，构成循环。`std::sort` 在这种比较器上是未定义行为。已放弃。

## 采用的方案

两处改动，都保持比较器是**固定元组的字典序**，严格弱序自然成立：

1. `add_exact` 增加 `alternative_reading` 参数。只有次要切分的调用传 `true`，其候选归入第 2 组，与单字同组竞争，由词频决定位置；
2. `better()` 中 `parse_rank` 由 `base_weight` **之前**移到**之后**。

第 2 点是必需的：仅做第 1 点时，主切分的全部单字仍会因 `parse_rank` 更小而排在「西安」之前，实测把「西安」压到 60 名开外。

## 结果

```text
xie    改前  西鄂  些  血  谢  写
       改后  些  血  谢  写  邪

xian   改前  西安  西岸  锡安  先  现
       改后  先  现  显  线  险
```

「西安」按自身词频 55003 落在第 18 位，位于 羡（60457）与 弦（52599）之间——即它应在的位置。

## 影响面

30 组常用输入的前 5 候选对照，**仅 `xie` 与 `xian` 两组变化，其余 28 组逐字节相同**。覆盖单音节（xi/e/ta/shi/wo/he/ci/qi）、双音节词（你好/中国/北京/测试/工作/苹果）、跨音节补全（问题/时间/什么/方法）等。

## 自动验证

- Windows x64 Release 全目标构建：通过，无警告；
- 完整 CTest 连跑四轮：**三轮 61/61**，一轮 60/61。

唯一失败项仍是 `piinput-host-process` 的冷启动计时门槛（38 MB 外部测试词库导致，压在 3000 ms 线上），与本次改动无关，说明见 `VERIFICATION_v0.7.10.md`，**门槛仍未调整**。

## 测试加固

`piinput-mode-indicator` 中「无光标信息时的回退位置」一项，原先断言落点在**主显示器**工作区内，而实现是钳制到**锚点所在显示器**的工作区。无光标时锚点取自当前前台窗口，整套测试连跑时那是别的测试留下的窗口，于是该断言依赖周围环境，出现过一次偶发失败。

已改为通过 `MonitorFromWindow` 取提示窗实际所在的显示器再比对。加固后连跑三轮全量测试均通过。

单独连跑该测试 40 次从未失败，因此无法在隔离环境下复现原失败；此处修正的是该断言与实现不一致这一确定问题，而非一个已复现的缺陷。

## 会话身份与回收（同版本内追加）

### 调查过程与证据边界

用户报告：默认语言设为中文，从其他输入法切换过来仍是英文。先确认其安装的确实是 0.7.11
（DLL 哈希与构建一致），说明先前三处修复已生效但问题仍在。

按开机时间切出 0.7.11 之后的日志（213 行），按进程还原模式序列：多数进程为干净的
「激活→中文」；出现英文的是 notepad++ 等用户实际打字的进程。

**此处未能定论**：Shift 切换没有埋点，「用户按了 Shift」与「宿主回报英文」在日志中无法区分。
曾加埋点以求分辨，但 `PiInputTSF.dll` 被十余个进程加载占用，无法就地替换验证。
因此这些条目既未被证实为缺陷，也未被排除。

### 沿此线查出的两个确凿缺陷

**会话键会碰撞。** `client_id` 取自 `GetCurrentProcessId()`，`session_id` 为每进程从 1 起的
计数，而 `SessionManager` 中 `erase`/`prune`/`evict` 出现 0 次。Windows 回收进程号后，
新进程呈递的是一对用过的键，被交回已退出进程的会话及其输入模式。
新增 `platform/windows/tsf/client_identity.{h,cpp}`，将进程创建时间与进程号混合。

**会话无上限累积。** 每次绑定输入上下文创建一个 `HostSession` 且永不释放，宿主运行整个登录会话。
新增按最近最少使用的回收，上限 64。

### 一处自我纠正

回收的第一版带有「不回收正在合成的会话」守卫。该守卫使回收在真实场景中永不触发：
中途放弃的窗口会永久保持合成状态。改为纯 LRU——活跃会话必然是最新的，
且被回收的会话可经既有 resume 路径重建。
