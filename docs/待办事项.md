### 1. `tsf_app_soak` 用例跑不起来（阻塞两项长稳中的一项）

**2026-09-10 更正**：此前记的成因是「`prepare_case` 用 `SetWindowTextW` 写种子文本，TSF 看不见」——那是推断，没验证过。实际把交互式测试构建出来跑，卡在更早的地方：

```
controls:true  layout:true  physical_keys:false  focus_isolation:false
```

`focus_isolation:false` 说明控制器没能把焦点稳定在自己的窗口上，按键去了别处，`physical_keys` 随之失败——根本没走到种子文本那一步。

真正的障碍是**这类测试需要独立桌面**。CMake 选项自己就写着「use only on an isolated desktop」：它靠 SendInput 真实敲键盘，只要用户在用这台机器、或者有别的窗口抢焦点，结果就不可信，还会把字打进别人的窗口。

下一步不是改 `prepare_case`，是先解决运行环境：要么在无人使用的时段跑，要么开一个独立的 Windows 桌面（`CreateDesktop`）把测试关进去。在那之前谈种子文本怎么写都是空的。

构建方式（已验证可编译）：


### 7. `update-source-manifest.ps1` 漏收中文文件名

v0.9.0 没有用它：改用只刷新既有条目的 `scripts/dev/update-sha256sums.ps1`，新文件手工追加。

## 无法靠改代码解决的

### 代码签名

无可信 Authenticode 签名与 RFC 3161 时间戳。开启智能应用控制强制模式的机器会在内核代码完整性层直接拒绝安装器，且不提供绕过入口。

微软的 Artifact Signing 服务排除中国大陆，只能走传统 CA。发布脚本里的签名开关已经备好。

签名必须用 **RSA**——Smart App Control 目前不支持 ECC 证书。

## 待查证的怀疑

### explorer.exe 的 GDI 泄漏是不是我们的（测量中）

**2026-09-10 已挂探针**，每分钟记一次 explorer 与几个加载了 shim 的进程的 GDI / USER / 句柄数，跑 8 小时，输出在会话 scratchpad 的 `gdi-samples.csv`。判据：explorer 在涨而加载了 shim 的进程不涨、且涨幅与 PiInput 使用量无关，就不是我们。


2026-08-28 观察到 explorer 的 GDI 对象数达到 9845（上限 10000），触发基于堆栈的缓冲区溢出对话框。

现有证据都指向**不是** PiInput：泄漏方向与使用量相反（PiInput 用得最多的 MobaXterm 422、notepad++ 318，几乎不用的 explorer 9845）；shim 里没有随按键增长的 GDI 创建路径；泄漏的是 GDI 对象而图标属于 USER 对象（explorer 的 USER 仅 1685）。

但**证否本身做不到**。要彻底排除，需要在 explorer 重启后挂探针记录它的 GDI 增长曲线，看它在完全不使用 PiInput 时涨不涨。

## 已知但不打算修的

### MobaXterm 里候选框不跟随光标

原理上做不到。该程序不维护系统光标，`GetTextExt` 与 `GetScreenExt` 都返回固定的退化矩形（实测 53 次不变），没有任何接口能问出插入点在第几行第几列——那个信息只存在于它自己的绘图代码里。

已评估并否决的方案：

- **屏幕捕获找闪烁光标**：时序对不上（闪烁周期 500ms–1s，而候选框必须在第一个字母按下时就位）；打字时画面本来就在变，合成串的变化特征与光标几乎相同；隐私代价不成立——把 SSH 会话的屏幕内容读进输入法进程，与输入法应有的可信度冲突。
- **键盘位置推算**：我们只看得见自己吃掉的键，看不见 shell 命令、Tab 补全、方向键和远端输出，位置会自信地漂移且无法自知。它还依赖 cell 尺寸和 viewport 原点，而那两个量本身要靠视觉方案提供。
- **DLL 注入 / hook 绘图函数**：为候选框位置付出的代价远超收益。

当前做法是稳定、不乱跳、落在输入区附近，并已写入随包文档，避免试用者误认为是缺陷。

## 已经处理掉的

### `PendingFileRenameOperations` 里的整目录删除（2026-09-10 解除）

曾经排着 `C:\Program Files\PiInput\Runtime\Shim` 和 `Runtime` 两条**整目录删除**，重启时有把安装抹掉的风险。

重启之后队列已被消费，而目录**没被删掉**——PFRO 删不掉非空目录，那两条是空操作。现在队列里 PiInput 相关只剩 6 条，删的都是 `.retired.*` 文件，而那些文件早已不存在，重启时同样是空操作。

**没有动注册表，这是有意的**：PFRO 是成对存储的（源 / 目标），删错一条会让后面所有操作错位，可能重命名或删掉别的东西。既然没有实际危害，动它的风险大于收益。
